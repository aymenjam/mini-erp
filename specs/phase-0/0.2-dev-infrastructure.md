# Spec 0.2 — Dev infrastructure

- Roadmap item: 0.2
- Status: implemented and checked by hand (2026-09-20). See "How it was checked".
- Depends on: ADR-004, ADR-005, ADR-007

## Goal
One command starts all infrastructure that the services need, on the developer machine,
and the same infrastructure is the base of the full container stack.

## Scope
- `docker-compose.dev.yaml`: PostgreSQL 18.6, Kafka 4.3.1 (KRaft, image `apache/kafka`), Schema Registry (`cp-schema-registry` 8.3.0),
  Keycloak 26.7.4.
- `infra/postgres/init/01-create-databases.sh`: one database and one own user per service
  (customers, inventory, sales, purchasing, invoicing, accounting) plus `keycloak`.
- `infra/keycloak/mini-erp-realm.json`: realm `mini-erp`, the six roles, one dev user per role, client `erp-frontend`
  (public, Authorization Code + PKCE), client `erp-test-cli` (password grant, for automated tests and curl only).
- `docker-compose.yaml`: includes the dev file. Services, gateway and frontend are added later.
- `.env.example` with all variables. `.env` is git-ignored.
- Health checks on all four containers. Start order with `depends_on: condition: service_healthy`.

## Acceptance criteria
- AC-1: With a `.env` copied from `.env.example`, `docker compose -f docker-compose.dev.yaml up -d` brings all four containers to `healthy`.
- AC-2: Without a `.env`, `docker compose` stops with a clear message that says which variable is missing.
- AC-3: From the host, `localhost:5432` lists the seven databases, and each service user can connect only to its own database.
- AC-4: A client on the host can create a topic, produce and consume with `localhost:9092`. A client in the Compose network can use `kafka:29092`.
- AC-5: `GET http://localhost:8081/subjects` returns `[]`.
- AC-6: `http://localhost:8080/realms/mini-erp/.well-known/openid-configuration` answers 200, and the issuer is `http://localhost:8080/realms/mini-erp`.
- AC-7: A token from `erp-test-cli` for each dev user contains exactly that user's role in `realm_access.roles`.
- AC-8: `erp-frontend` does not allow the password grant.
- AC-9: `docker compose up -d` (container mode) reaches the same result as AC-1 to AC-6, from empty volumes.
- AC-10: No secret is committed. Dev passwords come from `.env`, also inside the realm import file.
- AC-11: `docker compose down -v` followed by `up -d` gives a clean, working state again.

## How it was checked
On 2026-09-20 with Docker 29.7 / Compose 5.5 on arm64, all criteria by hand:
- Dev mode: AC-1, AC-3 to AC-8. The database check tried every user against every database (only the diagonal connects).
  All six dev users were tested for AC-7. Kafka was tested from a container on the host network, which uses the same `localhost:9092`.
- AC-2: `.env` removed, `docker compose config` names each missing variable.
- Container mode and AC-11: `down -v`, then `docker compose up -d` from empty volumes. AC-9 checks passed (seven databases, `[]`, realm 200).
An automated check script is not part of this spec.

## Out of scope
- Application containers, gateway and frontend (0.3, 0.4).
- Production settings: HTTPS, Keycloak `start` mode, multi-node Kafka, backups, resource limits.
- Kafka topic creation and schema registration (Phase 1).
- Kafka UI or database admin tools.
- Observability stack (Phase 6).

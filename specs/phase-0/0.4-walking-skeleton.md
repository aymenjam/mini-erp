# Spec 0.4 — Walking skeleton

- Roadmap item: 0.4
- Status: in progress, 3 of 4 slices done
- Depends on: 0.1, 0.2, 0.3

## Goal
Prove the full chain with the smallest possible feature:
a user logs in with Keycloak in Angular and sees a customer list (empty) served by `customers` through the gateway.
This is the exit criterion of Phase 0.

## Scope
1. **customers service** (`services/customers`, base package `org.j2ra.minierp.customers`), created by copying the template (0.3).
   One use case "list customers", through the input port `ListCustomersUseCase`. It returns an empty page for now.
   - `GET /api/v1/customers` returns the pagination shape from `constitution.md`, with `content: []`.
   - Allowed roles: `SALES`, `ADMIN`.
   - The endpoint has `@Operation` and `@ApiResponse`, and the response DTO has `@Schema` (rule R11, `docs/api-guide.md`).
   - `page`, `size` and `sort` are validated as in `constitution.md`, section 4 (`size` at most 100). `sort` is `field,asc|desc` with a
     whitelist per resource. In 0.4 the whitelist is only `id`: `sort=id,desc` is accepted, any other field gives 400. An invalid value
     gives 400 `application/problem+json`.
   - `spring-boot-starter-validation` (managed by the Boot BOM) is added to `customers` only, as an addendum to ADR-008. It is used only
     in `infrastructure.in.rest`.
   - Own database `customers`, Flyway baseline only. No customer table yet.
   - The service is created by following `docs/new-service.md`, and the time is measured.
2. **Gateway** (`services/gateway`): Spring Cloud Gateway from the Spring Cloud 2025.0.3 train.
   - Validates the JWT, routes `/api/v1/customers/**` to `customers`.
   - Explicit connect and response timeouts towards the services (environment variables, defaults in `.env.example`). The gateway answers 503 when a
     service refuses the connection, and 504 when it does not answer in time. Retries, circuit breaker and rate limiting stay in Phase 6.
   - Creates `X-Correlation-Id` if missing and passes it on.
   - CORS: the allowed origin `http://localhost:4200` applies in dev mode and in container mode (the browser is on `localhost:4200`, the
     gateway on `8090`). The origin comes from an environment variable.
   - In the dev profile only, it routes `/v3/api-docs` and Swagger UI of `customers`. Check that Swagger UI really loads through the
     route (path prefix, forwarded headers) and write the settings needed. They are dev only: `trusted-proxies` (the loopback addresses) in the
     `application-dev.yaml` of the gateway, and `server.forward-headers-strategy: native` in the `application-dev.yaml` of `customers` (the only change
     of `customers` in this slice). Then the OpenAPI `servers` URL is the gateway, and "Try it out" calls the gateway (measured, ADR-010).
   - In the dev profile only, the gateway lets `/swagger-ui.html`, `/swagger-ui/**` and `/v3/api-docs/**` pass without a token (a browser cannot send one when
     it loads the page), and `customers` does the same in dev only. The token is pasted by hand only for the API calls made from Swagger UI
     (`docs/api-guide.md`). Every other path still needs a token.
   - Gateway has no business logic and no database.
   - The gateway is not a copy of the service template, so the hexagonal ArchUnit rules do not apply to it. It has its own tests and its own smaller ArchUnit rule set (AC-22), and it
     follows the conventions of `constitution.md` that apply to a gateway: English only; paths under `/api/v1/<resource>`; Problem Details
     (`application/problem+json`, no stack trace) for the errors it creates itself; `X-Correlation-Id`; settings from environment variables
     listed in `.env.example`; stateless, no session and no cache (section 9). Pagination, money, ids, database and Kafka rules do not apply.
   - Lombok is not used in the gateway (no dependency, no `lombok.config`).
3. **Frontend** (`frontend/`): Angular 22 app.
   - Login with Keycloak, client `erp-frontend`, Authorization Code + PKCE.
   - Access token is sent to the gateway only. Logout ends the Keycloak session.
   - One route `/customers` behind an auth guard. Shows the list, or an "No customers yet" message when it is empty.
   - Shows the user name and a logout button. Shows a clear message on 401 and 403.
   - Besides `/customers`, the app has the technical route `/auth/callback`: the OIDC redirect target (added in slice 3,
     see "Changes to this spec").
4. **Run modes:** dev mode (services with Maven/IDE, `ng serve`) and container mode (Dockerfiles for gateway,
   customers and frontend added to `docker-compose.yaml`).
5. **ADRs** (no library without an ADR). The "Baseline libraries" ADR (0.3) does not cover the libraries of this spec:
   - **API gateway ADR** (roadmap 0.4): why Spring Cloud Gateway; the flavor (WebFlux or Server WebMVC), with the Boot 4.x
     migration (roadmap 6.6) in mind; JWT validation at the gateway and again in the services; CORS (allowed origin, methods,
     headers, exposed `X-Correlation-Id`, handled only at the gateway). It also lists the gateway starter and its security starter.
   - **Angular OIDC library ADR**: the library, checked for Angular 22 support (with the source), the "no token in `localStorage`"
     decision, and the frontend test tools.
   - **Docker images ADR**: the Node image of the CI job, the runtime image of the frontend, and the Keycloak image of the chain test.
     Exact tags, checked on the registry.
   - Keycloak in the chain test uses Testcontainers `GenericContainer` with the Keycloak image. No extra library.
     There is one realm file: `infra/keycloak/mini-erp-realm.json`. The client `erp-test-cli` stays in it as a dev and test only client
     (password grant enabled for this client only), and all dev users stay. The chain test reads this file from `infra/` (it finds it the
     way `ComposePostgresVersionTest` finds `docker-compose.dev.yaml`) and gives the placeholders fake values.
6. **Ports:** gateway `8090`, customers `8091`, frontend `4200`. They are added to: `.env.example` (the three ports), `README.md` (a port
   table), `docs/new-service.md` (a port table and the rule for the next free port) and `application-dev.yaml`.

## Acceptance criteria
- AC-1: In dev mode, user `sales` opens `http://localhost:4200`, is sent to Keycloak, logs in, and sees the empty customer list.
- AC-2: The same works in container mode with `docker compose up -d` after the images are built. The browser is on `http://localhost:4200`
  and the gateway on `8090`, so CORS (AC-13) applies in container mode too.
- AC-3: A user without a token gets 401 from the gateway on `/api/v1/customers`. A user with role `WAREHOUSE` gets 403. The 403 is
  produced by `customers` (roles are checked there). The gateway passes it on unchanged, with its `application/problem+json` body.
- AC-4: Direct call to `customers` without a valid token gets 401. Services do not trust the gateway alone.
- AC-5: In dev mode and in container mode, services accept a token issued via `http://localhost:8080/realms/mini-erp` and reject
  another issuer. The keys come from a `jwk-set-uri` that works in each mode (from the host in dev mode, from the compose network
  in container mode). In the chain test, Keycloak has a random port: the test starts Keycloak first, reads the mapped port, gets the
  token from that address, and starts `customers` and the gateway with the issuer and the `jwk-set-uri` built from the same port.
- AC-6: **Automated chain test (backend):** starts Keycloak (Testcontainers), PostgreSQL, the customers app and the gateway.
  The Keycloak of the test imports the realm file of `infra/` (the only realm file, see scope item 5) with fake values for its placeholders.
  The chain test lives in its own test module, not in a service module, because services do not depend on each other.
  Gets a token with `erp-test-cli`, and checks: `sales` gets 200 with `content: []`, no token gets 401, `warehouse` gets 403.
  It also checks CORS (AC-13). It runs in `./mvnw verify` and in the GitLab pipeline.
- AC-7: **Automated frontend tests:** the auth guard blocks a user who is not logged in. The customer list shows the empty message and shows an error message on 401 / 403.
  They run in the pipeline (new frontend job).
  AC-6 and AC-7 together are the automated coverage of the Phase 0 exit criterion in `roadmap.md`. The real browser login
  (Angular to Keycloak) is checked by hand in AC-1, because browser end-to-end tests are out of scope.
- AC-8: The response has the `X-Correlation-Id` header, and the same id appears in the logs of gateway and customers.
- AC-9: ArchUnit tests of `customers` are green (rules from 0.3). The controller calls `ListCustomersUseCase` only.
- AC-10: The use case has a unit test with a fake output port. No Spring in that test.
- AC-11: No token is stored in `localStorage` (decision recorded in the OIDC-library ADR).
- AC-12: `docs/` and `README.md` are updated. The owner updates `roadmap.md` (status `[x]`). The gateway ADR and the OIDC library ADR exist in `docs/adr/`
  and cover the points listed in scope item 5 (for the gateway: Spring Cloud Gateway, flavor, JWT validation, CORS).
  The OIDC ADR checks that the library supports Angular 22, with the source.
- AC-13: CORS at the gateway: a preflight `OPTIONS` request from `http://localhost:4200` is allowed (methods and headers of the
  ADR, `Authorization` and `X-Correlation-Id` included), and the browser can read `X-Correlation-Id`.
  A preflight from any other origin is not allowed. `customers` sets no CORS headers itself. This holds in dev mode and in container mode.
  The allowed origin comes from an environment variable.
- AC-14: The pagination parameters `page`, `size` and `sort` are validated (`size` at most 100, `sort` is `field,asc|desc` with the
  whitelist `id`). A test covers invalid values, including `sort` on another field (each gives 400 `application/problem+json`), and
  `sort=id,desc` is accepted. The addendum to ADR-008 for `spring-boot-starter-validation` (`customers` only, `infrastructure.in.rest`
  only) exists.
- AC-15: The customers endpoint is documented (`@Operation`, `@ApiResponse`, `@Schema`), the rule R11 is green, and `/v3/api-docs`
  lists it in the dev profile.
- AC-16: Through the gateway, in the dev profile only, `/v3/api-docs` and Swagger UI of `customers` are reachable without a token, and
  Swagger UI loads. AC-4 stays true for all other paths. Without the dev profile, `/swagger-ui.html`, `/swagger-ui/**` and `/v3/api-docs/**` give 401.
- AC-17: `customers` was created by following `docs/new-service.md`. The time is written in the "Progress" section (target
  15 minutes, AC-16 of spec 0.3). The guide is fixed if it was wrong.
- AC-18: The Docker images ADR exists in `docs/adr/` with exact tags.
- AC-19: `erp-test-cli` is defined once, in the dev realm, marked dev/test only. `README.md` says it must never exist in a production
  realm. The chain test uses the same file. The `README.md` sentence is written in slice 2 (the chain test module checks it).
- AC-20: The three ports are written consistently in the four places of scope item 6.
- AC-21: The gateway's own errors are `application/problem+json` with the right status: an invalid or expired token gives 401, an unknown
  route gives 404, `customers` down gives 503 (the service cannot be reached), and a `customers` that does not answer within the response
  timeout gives 504. The connect and response timeouts come from environment variables. Retries, circuit breaker and rate limiting are Phase 6.
  Each response has `X-Correlation-Id` and no internal detail in the body.
- AC-22: The gateway has a small ArchUnit rule set: no dependency on any service package, and no JPA, Kafka or JDBC classes.

## Delivery in 4 slices
This spec is built in four slices, one at a time, in this order. Each slice has its own
plan, verification and commit. The next slice starts only when the owner says so.

| # | Slice | Scope items | Acceptance criteria proven here |
|---|---|---|---|
| 1 | customers service | 1 | AC-4, AC-9, AC-10, AC-14, AC-15, AC-17 |
| 2 | Gateway | 2 and the OpenAPI route (dev only) | AC-3, AC-5 (dev mode), AC-6, AC-8, AC-13, AC-16, AC-19, AC-21, AC-22, gateway ADR (part of AC-12) |
| 3 | Angular frontend | 3 | AC-7, AC-11, AC-1 (by hand, with slices 1 and 2 running), OIDC ADR (part of AC-12) |
| 4 | Containers and documentation | 4 and the Docker images ADR | AC-2, AC-5 (container mode), AC-18, AC-20, AC-12 (docs and README) |

Rules for every slice:
1. Plan first: files, order, and how each criterion is verified. Wait for approval.
2. Implement only this slice. If work from another slice is needed, say so and ask.
3. Verify. Report each criterion as pass, fail or not verifiable locally, with the
   command and its output.
4. Update the "Progress" section in the same change, so my review covers it.
5. Show the diff and stop. I review. After my approval, make one commit:
   "feat(0.4): slice N - <name>". Do not push unless I ask.
6. Stop after the commit. Do not start the next slice.
7. If the spec is wrong or unclear, stop and propose a change to the spec.
   Do not deviate silently.

## Out of scope
- Customer CRUD, contacts, addresses, search, validation of customer data (item 1.1). Validation of the request parameters
  (`page`, `size`, `sort`) stays in scope.
- Role-based menus and screens (item 1.3). Only the guard and the two error messages exist.
- Routes to services other than `customers`.
- Kafka, events and outbox (item 1.4).
- Browser end-to-end tests (roadmap item 6.7, with an ADR for the tool).
- Refresh-token hardening, session timeout tuning, social login, user self-registration.
- Rate limiting, circuit breaker, retries at the gateway (Phase 6).
- A Keycloak login button in Swagger UI, and a separate API documentation of the gateway itself.
- UI component library, theming, i18n and generated API client (decided in an ADR before
  item 1.3). The skeleton uses plain Angular and minimal CSS. No component library is added.

# Spec 0.4 — Walking skeleton

- Roadmap item: 0.4
- Status: spec only, not implemented
- Depends on: 0.1, 0.2, 0.3

## Goal
Prove the full chain with the smallest possible feature:
a user logs in with Keycloak in Angular and sees a customer list (empty) served by `customers` through the gateway.
This is the exit criterion of Phase 0.

## Scope
1. **customers service** (`services/customers`, base package `org.j2ra.minierp.customers`), created by copying the template (0.3).
   One use case "list customers", through the input port `ListCustomersUseCase`. It returns an empty page for now.
   - `GET /api/v1/customers` returns the pagination shape from `constitution.md`, with `content: []`.
   - Allowed roles: `SALES`, `ADMIN`.
   - Own database `customers`, Flyway baseline only. No customer table yet.
2. **Gateway** (`services/gateway`): Spring Cloud Gateway from the Spring Cloud 2025.0.3 train.
   - Validates the JWT, routes `/api/v1/customers/**` to `customers`.
   - Creates `X-Correlation-Id` if missing and passes it on.
   - CORS for `http://localhost:4200` in dev.
   - Gateway has no business logic and no database.
3. **Frontend** (`frontend/`): Angular 22 app.
   - Login with Keycloak, client `erp-frontend`, Authorization Code + PKCE.
   - Access token is sent to the gateway only. Logout ends the Keycloak session.
   - One route `/customers` behind an auth guard. Shows the list, or an "No customers yet" message when it is empty.
   - Shows the user name and a logout button. Shows a clear message on 401 and 403.
4. **Run modes:** dev mode (services with Maven/IDE, `ng serve`) and container mode (Dockerfiles for gateway,
   customers and frontend added to `docker-compose.yaml`).
5. **ADRs** (no library without an ADR). The "Baseline libraries" ADR (0.3) does not cover the libraries of this spec:
   - **API gateway ADR** (roadmap 0.4): why Spring Cloud Gateway; the flavor (WebFlux or Server WebMVC), with the Boot 4.x
     migration (roadmap 6.6) in mind; JWT validation at the gateway and again in the services; CORS (allowed origin, methods,
     headers, exposed `X-Correlation-Id`, handled only at the gateway). It also lists the gateway starter and its security starter.
   - **Angular OIDC library ADR**: the library, the "no token in `localStorage`" decision, and the frontend test tools.
   - Keycloak in the chain test uses Testcontainers `GenericContainer` with the Keycloak image. No extra library.
6. **Ports (proposal):** gateway `8090`, customers `8091`, frontend `4200`.

## Acceptance criteria
- AC-1: In dev mode, user `sales` opens `http://localhost:4200`, is sent to Keycloak, logs in, and sees the empty customer list.
- AC-2: The same works in container mode with `docker compose up -d` after the images are built.
- AC-3: A user without a token gets 401 from the gateway on `/api/v1/customers`. A user with role `WAREHOUSE` gets 403.
- AC-4: Direct call to `customers` without a valid token gets 401. Services do not trust the gateway alone.
- AC-5: The token issuer is `http://localhost:8080/realms/mini-erp` in both modes, and services validate it.
- AC-6: **Automated chain test (backend):** starts Keycloak (Testcontainers, same realm file as `infra/`), PostgreSQL, the customers app and the gateway.
  Gets a token with `erp-test-cli`, and checks: `sales` gets 200 with `content: []`, no token gets 401, `warehouse` gets 403.
  It also checks CORS (AC-13). It runs in `./mvnw verify` and in the GitLab pipeline.
- AC-7: **Automated frontend tests:** the auth guard blocks a user who is not logged in. The customer list shows the empty message and shows an error message on 401 / 403.
  They run in the pipeline (new frontend job).
  AC-6 and AC-7 together are the automated coverage of the Phase 0 exit criterion in `roadmap.md`. The real browser login
  (Angular to Keycloak) is checked by hand in AC-1, because browser end-to-end tests are out of scope.
- AC-8: The response has the `X-Correlation-Id` header, and the same id appears in the logs of gateway and customers.
- AC-9: ArchUnit tests of `customers` are green (rules from 0.3). The controller calls `ListCustomersUseCase` only.
- AC-10: The use case has a unit test with a fake output port. No Spring in that test.
- AC-11: No token is stored in `localStorage` (decision recorded in the OIDC-library ADR).
- AC-12: `docs/`, `README.md` and `roadmap.md` are updated. The gateway ADR and the OIDC library ADR exist in `docs/adr/`
  and cover the points listed in scope item 5 (for the gateway: Spring Cloud Gateway, flavor, JWT validation, CORS).
- AC-13: CORS at the gateway: a preflight `OPTIONS` request from `http://localhost:4200` is allowed (methods and headers of the
  ADR, `Authorization` and `X-Correlation-Id` included), and the browser can read `X-Correlation-Id`.
  A preflight from any other origin is not allowed. `customers` sets no CORS headers itself.

## Out of scope
- Customer CRUD, contacts, addresses, search, validation (item 1.1).
- Role-based menus and screens (item 1.3). Only the guard and the two error messages exist.
- Routes to services other than `customers`.
- Kafka, events and outbox (item 1.4).
- Browser end-to-end tests (roadmap item 6.7, with an ADR for the tool).
- Refresh-token hardening, session timeout tuning, social login, user self-registration.
- Rate limiting, circuit breaker, retries at the gateway (Phase 6).

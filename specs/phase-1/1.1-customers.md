# Spec 1.1 — Customers

- Roadmap item: 1.1
- Status: 0 of 3 slices done
- Depends on: 0.3, 0.4

## Goal
The `customers` service manages real customer data: create, read, update and deactivate a customer, with contacts and
addresses, validation, pagination and search. Every endpoint is documented with OpenAPI.

## Scope
1. **Aggregate `Customer`.** One aggregate is one transaction. Contacts and addresses live inside it.
   - Fields: `id` (UUID v4, created in the domain with `UUID.randomUUID()`, as in `constitution.md`), `type` (`COMPANY` or `INDIVIDUAL`), `name` (required, 1 to 200 characters: company name or full name),
     `email` (optional, valid format), `phone` (optional), `vatNumber` (optional, `COMPANY` only, unique when present),
     `status` (`ACTIVE` or `INACTIVE`), `createdAt`, `updatedAt` (UTC, `Instant`), `version` (`@Version`).
   - **Contact** (0..n): `id`, `firstName` and `lastName` (required), `email`, `phone`, `jobTitle`, `primary` (at most one per customer).
   - **Address** (0..n): `id`, `type` (`BILLING` or `SHIPPING`), `line1` (required), `line2`, `postalCode`, `city` (required),
     `country` (ISO 3166-1 alpha-2, required), `defaultForType` (at most one default per type and per customer).
   - Business rules are in `domain` (plain Java, no Spring): one primary contact, one default address per type,
     `vatNumber` only for `COMPANY`, and an `INACTIVE` customer cannot be changed except by reactivating it.
2. **REST API** under `/api/v1/customers`. Errors are Problem Details. Every endpoint has `@Operation`, `@ApiResponse` and `@Schema` (rule R11).

   | Method and path | Use case | Roles |
   |---|---|---|
   | `POST /customers` | create | SALES, ADMIN |
   | `GET /customers/{id}` | get, with contacts and addresses | SALES, ADMIN |
   | `PUT /customers/{id}` | update main fields (needs `version`) | SALES, ADMIN |
   | `POST /customers/{id}/deactivate`, `POST /customers/{id}/reactivate` | change status | SALES, ADMIN |
   | `GET /customers` | list and search (slice 3) | SALES, ADMIN |
   | `POST /customers/{id}/contacts`, `PUT` and `DELETE /customers/{id}/contacts/{contactId}` | manage contacts | SALES, ADMIN |
   | `POST /customers/{id}/addresses`, `PUT` and `DELETE /customers/{id}/addresses/{addressId}` | manage addresses | SALES, ADMIN |

   - There is no `DELETE /customers/{id}`. Later, orders and invoices will point to a customer, so we deactivate instead.
     A contact or an address can be deleted: they are parts of the aggregate.
   - Create gives 201 with a `Location` header. Unknown id: 404. Duplicate `vatNumber`: 409. Old `version`: 409. Invalid body: 400 with the list
     of invalid fields. Change on an `INACTIVE` customer: 409.
   - Contact and address endpoints load the aggregate, change it and save it once. `@Version` protects concurrent edits.
3. **Persistence.** Flyway migrations (never edit an applied one; `V1` stays as it is):
   - `V2__customer.sql` (slice 1): table `customer`, unique index on `vat_number` (where not null).
   - `V3__customer_contact_and_address.sql` (slice 2): tables `customer_contact` and `customer_address`, foreign keys with `ON DELETE CASCADE`,
     partial unique indexes for "one primary contact" and "one default address per type".
   - JPA entities have no setters and are mapped by a `CustomerPersistenceMapper` (`docs/jpa-entities.md`). The stub `CustomerPersistenceAdapter` is replaced.
4. **Search and pagination** (slice 3): `GET /customers?q=&type=&status=&page=&size=&sort=`.
   - `q`: case-insensitive "contains" on `name`, `email` and `vatNumber`. `%` and `_` in `q` are escaped. At most 100 characters.
   - `type` and `status`: exact filters. An invalid value gives 400. Without a filter, both statuses are returned.
   - `sort` whitelist: `id`, `name`, `createdAt`. Default: `name,asc`. Other rules: `constitution.md` section 4, as in spec 0.4.
   - A list item is a summary (`id`, `type`, `name`, `email`, `status`), not the full aggregate.
5. **Libraries.** None new expected (JPA, Flyway, PostgreSQL and validation are already in `customers`). If one is needed: ask the owner and write an ADR first.
6. **Frontend.** Not changed here (item 1.3). The list response keeps the pagination shape, so the current screen still works.

## Acceptance criteria
- AC-1: A `COMPANY` and an `INDIVIDUAL` customer can be created (201, `Location`, `status=ACTIVE`, `version=0`).
- AC-2: Missing or too long `name`, bad email, bad country code, and `vatNumber` on an `INDIVIDUAL` give 400 `application/problem+json`
  with the field names and no stack trace.
- AC-3: Get by id returns the contacts and addresses. An unknown id gives 404.
- AC-4: An update with the right `version` works and increases it. An old `version` gives 409. Tested with two concurrent updates on real PostgreSQL.
- AC-5: A duplicate `vatNumber` gives 409, also with two concurrent creates (the database constraint decides).
- AC-6: Deactivate and reactivate work. An `INACTIVE` customer refuses changes (409), except reactivate. `DELETE /customers/{id}` does not exist.
- AC-7: Contacts can be added, updated and deleted. Rule for a second primary contact (replace or refuse): decided in the plan of slice 2.
- AC-8: Addresses can be added, updated and deleted. One default per type and per customer is guaranteed by the domain and by the database index.
- AC-9: Search `q` finds a customer by name, email and VAT number, ignoring case. `%` in `q` is a normal character.
- AC-10: Filters `type` and `status` work alone and with `q`, pagination and sort. `sort` on a field outside the whitelist gives 400.
- AC-11: SALES and ADMIN can read and write. WAREHOUSE and a user without role get 403. No token gives 401. Checked on every endpoint, as in `CustomerSecurityTest`.
- AC-12: Every endpoint has `@Operation`, `@ApiResponse` (success and errors) and `@Schema` with examples. Rule R11 is green.
  `/v3/api-docs` lists them in the profile `dev` only.
- AC-13: The domain has plain unit tests (no Spring). Use cases have tests with fake ports. ArchUnit rules are green and unchanged.
- AC-14: The Flyway migrations apply on an empty database and validate (`FlywayValidationTest`). `V1` is not edited.
- AC-15: The chain test (gateway and customers) still passes. `./mvnw -B verify` is green.
- AC-16: `docs/api-guide.md` has customer examples, and `README.md` is updated if needed. The owner updates `roadmap.md`.

## Out of scope
- Kafka event `CustomerCreated` and the outbox (item 1.4).
- Angular screens and role-based menus (item 1.3).
- Customer number (business number), credit limit, payment terms, price lists, tags, notes, attachments.
- Tax exemption rules and currency per customer (invoicing owns VAT, Phase 4).
- Full-text or trigram search (needs a PostgreSQL extension and maybe an ADR), search inside contacts or addresses.
- Import and export, audit history, GDPR erasure.
- Address validation with a postal service.
- Local customer copy in sales (item 2.5).
